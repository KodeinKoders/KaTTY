# AGENTS.md

Guidance for AI agents working on KaTTY, a terminal emulator written in Kotlin with Compose for Desktop.
`README.adoc` describes the project for humans, this file is about how to work on it.

## What it is

KaTTY runs the user's login shell in a terminal drawn on a Compose `Canvas`.
The emulation is done by [libghostty-vt](https://ghostty.org) (called through Java FFM, not JNI or JNA), the pseudo-terminal by [pty4j](https://github.com/JetBrains/pty4j).
It only runs on macOS on Apple Silicon for now: that is the only platform libghostty-vt is built for.
The build needs JDK 25 (Gradle downloads it), because FFM is final there.

## Modules

`app` → `terminal-compose` → `terminal` → `ghostty-vt` → `libghostty-vt/` (a prebuilt dylib and its headers, not a Gradle module).
`app` also uses `app-core` → `terminal`, and `terminal-themes` → `terminal`. `iterm2-color-schemes/` holds the color schemes it packs (not a Gradle module either).

| Module | Package | Role |
| --- | --- | --- |
| `app` | `app.katty` | The application: a Jewel `DecoratedWindow` (it runs on the JetBrains Runtime, see its `build.gradle.kts`) that shows the terminals of the projects. |
| `app-core` | `app.katty.core` | What the application keeps and knows, with no Compose: where it writes (`KattyDirectories`), and what the steps of `plan.adoc` add. |
| `terminal-compose` | `app.katty.terminal.compose` | `Terminal`, the composable. Draws frames with the bundled JetBrains Mono, translates key events. |
| `terminal-themes` | `app.katty.terminal.themes` | `ITermColorSchemes`: the 811 `.itermcolors` schemes as `TerminalTheme`s, parsed on demand with kotlinx.serialization and xmlutil. The files and an `index.txt` of their names are copied into the resources by `prepareColorSchemes`. |
| `terminal` | `app.katty.terminal` | `TerminalSession`: a program in a PTY, its output fed to a terminal, published as immutable `TerminalFrame`s. Has its own key, frame and theme model. |
| `ghostty-vt` | `app.katty.ghostty` | Kotlin API over the jextract-generated FFM bindings (`…ghostty.ffm`, Java, committed). |

**Nothing above `terminal` mentions `ghostty-vt`**: `terminal` converts in `Mapping.kt`, and `ghostty-vt` is only an `implementation` dependency of it.
Keep it that way.
The generated Java is never part of an API: no `MemorySegment` or generated type leaves `ghostty-vt`.

## Commands

```shell
./gradlew build            # everything, with the tests: what CI runs
./gradlew :app:run         # opens the window
./gradlew :app:hotRun      # opens it with Compose Hot Reload, which the MCP server needs
./gradlew :terminal:test   # one module
```

`ghostty-vt/jextract.sh` regenerates the bindings and the key enums (`GhosttyKey`, and `TerminalKey` of `terminal`) after libghostty-vt is updated.
It needs jextract for JDK 25 on the `PATH`, or in `$JEXTRACT`.
`libghostty-vt/README.adoc` has the update procedure and says which Ghostty commit the dylib comes from.

## Build conventions

The Gradle build follows the Kodein conventions (the `kodein-gradle-kotlin-project` skill has them in full).
The ones that are easy to break:

- Kotlin DSL only. No coordinate in a build script: dependencies and plugins come from `gradle/libs.versions.toml`, and project dependencies use typed accessors (`projects.terminalCompose`).
- Every catalog plugin is also declared in the root `build.gradle.kts` with `apply false`. Catalog sections are sorted, with a blank line between domains, and each `[versions]` entry has a comment with its release page.
- Every module sets `jvmToolchain(findProperty("jvm.toolchain")!!.toString().toInt())`. The version is in `gradle.properties`.
- Repositories are declared in `settings.gradle.kts` only.
- A line that is not obvious in a build script gets a comment saying why.

## Threads

- A `GhosttyTerminal` is **not thread-safe**. In a session, one lock guards it, and the key encoder that reads it.
- The `GhosttyRenderState` belongs to the frame producer thread: only its `update` reads the terminal, so only that is under the lock.
- Callbacks of the terminal run on the thread that wrote to it, under the lock: they must only enqueue, and an exception must never escape them (it would take the JVM down).
- The producer waits for the output to pause (3 ms, at most 8) before it makes a frame. A program redraws in several writes that are read separately, and zsh moving the selection in its completion menu moves the cursor down to the menu, draws, and moves it back: a frame made after the first write shows the cursor in the menu for a frame. Do not make it publish at the first chunk of output.
- The frame producer publishes at most 60 frames per second. A row that did not change is **the same object** in the next frame (the renderer's cache relies on it): do not break that by creating rows needlessly.

## Keyboard and mouse

- Printable text comes from AWT's `KEY_TYPED` events, so that dead keys, input methods and Option characters work. `KEY_PRESSED` is only used for keys without text and for Ctrl combinations.
- While the terminal has the Compose focus it also has an input method session (`terminalTextInput`): that is what makes macOS report a dead key while it is composed, which is drawn underlined at the cursor (the preedit, kept in `TerminalTextInput`, drawn by `TerminalView`, never written to the terminal). The final character may then come as a `KEY_TYPED`, as committed text of the input method, or as both, depending on the platform: `TerminalTextInput.deliver` sends it **once**, so send text through it, not straight to the session. The `TerminalTextInput` DEBUG log tells which route delivered what.
- The session follows the **Compose** focus, not the window's: opening or closing one moves the AWT focus for a moment, which would close and open it again.
- An open session makes macOS show the accents menu when a letter is held: `app` registers `ApplePressAndHoldEnabled=false` at startup (`disablePressAndHold`, FFM calls to the Objective-C runtime). Any other program that shows the `Terminal` has to do the same.
- Compose's `KeyEvent` does **not** expose the AWT event: read it with Compose's public API (`Key.nativeKeyCode`, `utf16CodePoint`, `type`). Typed characters have the type `Unknown`.
- Option is not the program's Alt. Command shortcuts are not sent to the program. The exception is the **line editing keys of macOS** (`lineEditingText`, taken in `Terminal` before `KeyTranslator`): Option + Left / Right is `ESC b` / `ESC f`, Command + Left / Right / Backspace is `^A` / `^E` / `^U`, which is what Ghostty and iTerm2 send. Encoded as keys (`CSI 1;3 D`…) a shell does not know them and prints the end of the sequence. They go through `TerminalSession.sendText`, whatever keyboard mode the program is in, and with Shift or Control held they stay the program's.
- The text of a key event given to the encoder is the character as typed, before any Ctrl transformation (`"c"` for Ctrl+C). libghostty's encoder is not xterm's: Shift+Enter and Ctrl+I are distinct sequences even without the Kitty protocol.

## Tests

- The tests are real: they start programs in a PTY (`/bin/sh`, `seq`, `od`, `stty`), call the native library, and draw with Skia in memory. They wait on conditions with timeouts and never on fixed sleeps, except where time is what is tested.
- A test that waits reports the last screen when it times out: keep doing that.
- The rendering tests keep their images in `terminal-compose/build/renders`: look at them when you change how something is drawn.
- A new test should be shown to fail without the change it covers.

## Running the app

Starting the app opens a window on the user's desktop, and the user may be working in it or around it. So:

- **Never type into the app** with synthesized keystrokes (`osascript`, `Robot`, …): without a guarantee about the focused window they land in the user's other applications.
- **Never take a full-screen screenshot.** Capture the app's own window only: with the Compose Hot Reload MCP tool `take_screenshot`, or `screencapture -l <window id>`.
- **Several instances may run**, for instance one started from the IDE. Identify yours by process id, and stop only it.
- `./gradlew :app:hotRun` does not pass `--enable-native-access=ALL-UNNAMED`, which `:app:run` does: it prints JVM warnings at startup.

`.mcp.json` registers the Compose Hot Reload MCP server (`hotMcpServer`): the app must be started with `hotRun`, not `run`, for it to connect.
It is slow to start (`--no-daemon`), and its tools that work through semantics (`click`, `type_text`, `get_semantic_tree`) do nothing for the terminal, which is a `Canvas`.

- The mouse goes `Terminal` → `MouseTranslator` → `TerminalSession.sendMouse` → libghostty's mouse encoder, and only while the program asked for it (`TerminalFrame.mouseTracking`). **Positions are in cells (fractional) from `Terminal` to the session**, which converts them with the whole-number cell size it gave the terminal in `resize`: what a program is told of the size of a cell and what SGR-Pixels reports must agree, and a rounded float cell width drifts by dozens of pixels at the last column.
- **Selecting text** is the terminal's and the program is told nothing: with the left button when the program did not ask for the mouse, and with Shift + left button when it did (`SelectionDriver` decides, before `MouseTranslator` sees the event). The gesture is libghostty's (`GhosttySelectionGesture`: double click a word, triple click a line, Option+Command a block), installed in the terminal, which gives each row's selected cells to the render state; `TerminalFrame.selection` has them, outside the rows so that selecting does not change them. Selecting does **not** copy: the clipboard is the user's. The text of the last selection is kept in memory (`PrimarySelection`) for a **middle click**, which pastes it (when the program did not ask for the mouse, and with Shift when it did); it stays when the selection goes. Copy and paste are keys, handled before the program sees them: Command + C / V on macOS, Control + Shift + C / V elsewhere (`clipboardShortcut`; Control + C is the program's interrupt). A paste (key or middle click) goes through `TerminalSession.paste`, which follows the program's bracketed-paste mode and replaces the control bytes that could be taken for commands, and counts as typing (it unselects and snaps to the bottom). There is no confirmation for a multi-line paste into a program that did not ask for bracketed paste, which Ghostty has. What is typed for the program, and the program writing over selected cells (the session sees a row of the selection change), unselect: libghostty does neither. A press that was sent has its release sent whatever Shift does, and a gesture that started selecting finishes selecting. Shift on the wheel is not a bypass: it is how AWT says that the scroll is horizontal.
- The pointer (`terminalPointerIcon`): the arrow over the scrollbar (or while its thumb is dragged), else the cross when a drag would select a block (Option and Command held, and the left button selects), else the arrow while the program has the mouse, the I-beam with Shift held then or when it does not, or the shape the program asked for.
- A trackpad's wheel is fractions of a notch: they are added up, one report per whole notch, at most 10 per event.
- The pointer's shape follows what the program asked for (`TerminalFrame.pointerShape`, OSC 22; the text cursor by default).

- **The history** is scrolled by the session in whole rows (`scrollBy`, `scrollPage`, `scrollToTop`, `scrollToBottom`, `scrollToRow`, `scrollWheel`), and where the viewport is comes back in every frame as `TerminalFrame.scrollbar` (`null` when there is no history, which is also the case of the alternate screen). A notch of the wheel is 3 rows (`WheelScroller` adds the fractions of a trackpad up). With the mouse asked for the wheel is the program's; without it, it scrolls the history, or sends arrow keys on the alternate screen (alternate scroll, mode 1007). Shift + PageUp / PageDown / Home / End scroll it, and are consumed (the release too) only while there is history. Typing for the program snaps back to the bottom; output does not move the view.
- **The amount of a wheel event is normalized** (`WheelNormalizer`, in `Terminal.kt`'s pointer loop): macOS reports a slow click of a mouse wheel as 0.1 of a notch, which Java passes on as the precise rotation, so adding fractions up scrolled one click in three or four (one in ten with the mouse reported). A click is an event with a non-zero rounded rotation that comes alone (no scroll event in the 100 ms before): it is at least a notch, as Ghostty does it; a trackpad's stream keeps its fractions. `org.slf4j.simpleLogger.log.app.katty=debug` logs what the mouse gives.
- **The scrollbar** is drawn by `TerminalView` over the right edge, but its pointer is handled in `Terminal`'s own pointer loop (`ScrollbarInteraction`), not by a sibling composable, which would take the wheel events of its strip from the terminal. It fades out after a second.
- **Autoscroll while selecting:** a drag that is past the top or the bottom makes `selectionDrag` answer `UP` or `DOWN`, and `SelectionAutoscroll` ticks `selectionAutoscroll` every 50 ms with the last position. libghostty's tick scrolls the viewport itself: do not scroll in addition. A pointer that leaves with a button down is an `Exit` event: it is a drag that goes on.

## Images

- The **Kitty graphics protocol** is implemented by libghostty (parsing, chunks, zlib, raw RGB/RGBA/gray, placements, deletion, animation): KaTTY gives it what it asks of the embedder and draws what it keeps. The **PNG decoder** is a process-global setting (`ghostty_sys_set`) that `NativeLibrary` installs once with `javax.imageio` (it never throws into native code), and each terminal has a **storage limit** (`TerminalSession.start` gives 320 MB): without it nothing is stored.
- `TerminalSession.produceFrame` reads the placements for **every frame while the storage is not empty** (scrolling moves them with no change of the storage), copies an image's pixels once per generation under the lock, converts them to RGBA outside it, and keeps them in a cache that is pruned to the ids that have a placement. `TerminalFrame.images` has them in **cells** (fractional, positive or negative), not pixels, since libghostty sizes them with the whole-number cell size that the session gave it and the renderer measured another. A `TerminalImage` is the same object while it does not change: `ImageBitmapCache` keys on it.
- The renderer draws the layers (`z`) around the text: below the cell backgrounds, below the text, above the text, clipped to the terminal, with the edges on whole pixels.
- The session gives the terminal a cell size (8 × 16) at start: an image sent before the first `resize` would otherwise be placed on cells of no size.
- **Sixel and iTerm2 inline images are turned into Kitty transmissions** by `OutputTranslator`, in the reader, before `vtWrite`: libghostty drops a DCS Sixel and an `OSC 1337 ; File=` with no hook, so the stream is the only place to see them. A `DCS … q … ST` is held whole and decoded by `SixelDecoder` (raster attributes, repeats, RGB and HLS registers with the DEC hue origin, the VT340 palette, unset pixels transparent, 16 megapixels at most), an `OSC 1337 ; File=…` by `Iterm2Image` (`inline=1` only; `width` / `height` as `N`, `Npx`, `N%`, `auto`; `preserveAspectRatio`; `doNotMoveCursor`; the file decoded by `javax.imageio`: PNG, JPEG, GIF, BMP and the TIFF that chafa sends). Both are written **in place** as `ESC _ G a=T,f=32,s=,v=,q=2,m=… ; <base64> ESC \` chunks of 4096 characters (`KittyImageEncoder`), with no `i=` so that the id cannot be a program's own: libghostty then does the placement, the scrolling, the deletion and the storage limit, and nothing here draws them. The cursor is where Kitty leaves it (after the image, on its last row), except after a **Sixel, which gets a `CR LF`** as in xterm. A string that is over `maxPayload` (32 MB), or that cannot be decoded, is dropped and the parser goes on after it. APC, PM and SOS strings pass untouched (a Kitty chunk can hold anything).
- **The terminal answers device attributes** (`GhosttyTerminal.fillDeviceAttributes`, through `OPT_DEVICE_ATTRIBUTES`): DA1 is conformance 62 with ANSI color (22) and **Sixel (4) unless `start(advertiseSixel = false)`**, DA2 is `1;10;0`, DA3 a unit id of 0. Before, it did not answer at all, so a program that probes (chafa, vim, tmux, img2sixel) learned nothing. It is a capability and not an identity: `TERM` stays `xterm-256color`, and chafa now picks Sixel by itself (a plain `chafa file.png` draws an image). `-f kitty` is still the best for chafa, which does not probe for Kitty graphics.
- **Unicode placeholders** (the Kitty virtual placements of tmux and `kitten icat --unicode-placeholder`): libghostty keeps the placement (`U=1`) and flags the rows that hold placeholder cells (`GHOSTTY_ROW_DATA_KITTY_VIRTUAL_PLACEHOLDER`, `GhosttyRenderRow.hasPlaceholder`), and **the cells are decoded here** (`GhosttyPlaceholders.kt`: `U+10EEEE` plus diacritics for the row, the column and the high byte of the id, from the 297-entry table; the image id is the foreground color, a palette index as it is and an RGB as 24 bits, and the placement id is the underline color, both read from the full `GhosttyStyle` and not from the resolved RGB). In the frame the cell is **blank** (`TerminalCell.text` empty, its background kept, `TerminalCell.placeholder` has what it said), and `placeholderRuns` / `placeholderPlacement` (`PlaceholderLayout.kt`, pure, a port of Ghostty's `graphics_unicode.zig`) make one `TerminalImagePlacement` for each run of one row on the `BELOW_TEXT` layer: the image is fitted in the grid of its virtual placement (`c × r` cells, else its own size), centered, and each run shows its columns of it. A run is one row; a cell joins it when it has the same low id, the same placement id, a row that is omitted or equal, a column that is omitted or the next, and a high byte that is omitted or equal; the first cell takes what it omits as 0. The images of virtual placements are copied like the others. Because the placements come from the cells, they scroll, wrap and go with the text with no rule of their own.
- An answer of the terminal (`ESC _ G i=1;OK ESC \`) is **input** of the program: a test whose program reads a key must use `q=2`, which turns the answers off, as chafa does.
- Not drawn: the multipart iTerm2 variant (`MultipartFile`, `FilePart`, `FileEnd`) and Sixel through tmux's passthrough. **Not verified on a real program: `kitten icat`, tmux's placeholders, and Sixel from `img2sixel`, `timg` or `lsix`** (chafa's output is what the decoder was checked against, with the specification and hand-made streams).

## What the host is told

`TerminalSession` is meant to be embedded in an application that has many terminals: besides `frames` and `exited` it publishes `title`, `workingDirectory`, `progress` and `programStatus` (state flows, a `StateFlow` that has the last value) and `events` (`TerminalEvent`: `Bell`, `Notification`, `ClipboardWrite`, `PromptStarted`, `CommandStarted`, `CommandFinished`, `ResizeRequested`; a `SharedFlow` **without replay**, so a collector that comes late misses what happened before, and nobody collecting drops them). A frame has `alternateScreen`, and a cell `hyperlink`.

- libghostty calls back **synchronously, inside `vt_write`**, on the reader thread, under the lock (`GhosttyTerminal.onBell`, `onTitleChanged`, `onPwdChanged`, `onNotification`, `onProgress`, `onSemanticPrompt`, `onClipboardWrite`, `onReset`). They follow the rules of the threads: they only record or enqueue (`tryEmit` on a buffered `SharedFlow` that drops the oldest), and an exception never escapes (`guarded`). Strings that come with them are copies.
- **The title and the directory are not read in their callbacks**: libghostty says the title can be read after the callback returns. The callback sets a flag and `publishAfterWrite` reads `terminal.title` / `terminal.pwd` once `vtWrite` has returned, under the same lock. A reset (RIS) clears them without calling those callbacks, so `onReset` sets the same flags. `workingDirectory` is a path: `decodeWorkingDirectory` turns a `file://host/path` URI into it and removes the percent-encoding.
- **The clipboard** (OSC 52): a write is allowed by default and becomes `TerminalEvent.ClipboardWrite` (`start(clipboardWrite = false)` refuses it); `Terminal` puts it in the system clipboard, or in what a middle click pastes for the primary selection. A **read** is refused unless the host gives `start(clipboardReader = …)`, and it is the one callback that **blocks**: libghostty wants the answer before it returns, so the function runs on the reader thread and the program's output waits for it. Installing a reader also makes libghostty send the program paste events (mode 5522): `setClipboardReader` only installs it when there is one.
- **Shell integration** (`ShellIntegration`, on by default, `start(shellIntegration = false)` turns it off): a shell does not send OSC 7 (directory) and OSC 133 (prompts) on its own, so for zsh, bash and fish started as a login or interactive shell the session makes them read KaTTY's scripts (`terminal/src/main/resources/app/katty/terminal/shell-integration`, copied once to a temporary directory) and then the user's own files. zsh: `ZDOTDIR` points to a `.zshenv` that puts it back (the user's is saved in `KATTY_ZDOTDIR`), reads the user's, and loads the integration. bash: `--rcfile` points to the script, which reads the files of a login shell, or `~/.bashrc`, and installs its hooks after them. **`--posix` with `ENV`, which Ghostty and kitty use, does not work: the bash 3.2 of macOS does not read `ENV` that way.** fish: KaTTY's directory is put in front of `XDG_DATA_DIRS` (with `/usr/local/share:/usr/share` behind it when it was unset), fish reads `fish/vendor_conf.d/katty-shell-integration.fish` of it before the user's configuration, and the script takes the directory out of `XDG_DATA_DIRS` and sets its hooks (`fish_prompt`, `fish_cancel`, `fish_posterror`, `fish_preexec`, `fish_postexec`, `PWD`) at the first prompt. There is no mark B for fish, which has no `PS1`. **fish is not installed on the machine this was written on: the script was never run** (adapted from Ghostty's), the wiring is tested and the tests that run fish are skipped when it is not there. A prompt theme that rewrites `PS1` after the first prompt can lose the mark of the end of the prompt (B) for that prompt; the other marks do not depend on it. Any other shell, and a command with other arguments, is started as it is.
- **Program status** (OSC 7501, `programStatus`): libghostty validates the report and calls back, and **keeps no record**: `ProgramStatusStore` does, as the specification says (one record for each id, replaced as a whole by its next report; a clear removes the record and the ones beneath it, an empty id all of them; an empty app is the nearest ancestor's, resolved when read; `working` and `blocked` go at the next prompt (`PROMPT_START`) and when the program exits; 256 records at most, the one updated longest ago first). A reset (RIS) comes as a clear report with no id. The title and the message are the program's text: the direction marks and the invisible characters are removed (`clean`), the joiners that emoji need are kept. libghostty answers `OSC 7501 ; ?` by itself because the callback is set. The host removes what it showed with `clearProgramStatus`.
- **A request to resize the window** (`CSI 8 ; rows ; columns t`) is `TerminalEvent.ResizeRequested(columns, rows)` (`null` for 0, keep what it is): the session resizes nothing, the host decides, and any program can ask. `Terminal` does nothing with it.
- **Prompt marks** are what `scrollToPrompt(delta)` and the keys Command + Up / Down (Control + Shift + Up / Down elsewhere, `promptJump`) use: they only work when the shell sends them, and, like the history keys, only while there is history (otherwise the program gets them).
- **Links** (`session.linkAt(column, row)`): one that a program marked (OSC 8, which libghostty gives per cell and as an address through a grid ref, with no way to get its `id=`) or one written in the row's text (`findUrl` in `TerminalLinks.kt`, which has no URL detection from libghostty: it ends at whitespace and drops the punctuation of a sentence and a closing bracket without its opening one; one that wraps onto the next row is found whole: `TerminalRow.wrapped` is libghostty's soft-wrap flag of the row, `TerminalLink.segments` has a `TerminalLinkSegment(row, columns)` for each row that it is on, and the written text of the rows that wrap is searched as one line, up to 16 rows from the one asked; a marked link goes on onto the next row while the cell there has **the same address**, which stands in for the `id=` that is unreadable, so two links of the same address that touch are one). With Command held (Control elsewhere; `linkModifier`) `LinkInteraction` underlines the link under the pointer and shows the hand, and a left click on it opens it through `Terminal(onOpenLink)`, **before** the selection and the program's mouse see it: the program is told nothing of that click. The default opener only opens `http`, `https`, `ftp`, `file` and `mailto`.

### Focus, visibility and configuration

- **Focus reporting (mode 1004)**: `Terminal` calls `session.setFocused(active)` (`active` is "the keys go to this terminal": Compose focus and window focus), **after waiting 50 ms**: the effect is restarted when `active` changes, so that the focus moving for a moment while the input method session opens or closes tells the program nothing (vim would get a lost and a gained). The session only sends when the focus changes, and only if the program asked (`encodeFocus` checks the mode: `ghostty_focus_encode` does not); it starts not focused, so a program that turns the mode on is told nothing until the focus changes. It is not what is typed: it does not unselect nor scroll to the bottom.
- **`session.setVisible(false)`** stops the frame producer for a terminal that is not shown, and **lets go of what the session holds for the next frame**: the producer waits in its loop (a request that came meanwhile is kept, and showing the session again makes **one** frame), `frames.value` becomes a blank frame of the same size (one shared empty row, no cursor, no images), the row cache and the image cache are cleared, and once the terminal is quiet (1 s without output) the history is **compressed** by libghostty in bounded steps under the lock (`GhosttyTerminal.compress(INCREMENTAL)`, stopped and restarted by the activity token, 41 MB of history went to 1.3 MB resident in a measurement); reading it decompresses it, so nothing is lost. Showing the session reads every row again (the cost of a theme change). The terminal is still fed, keys, mouse and replies still go out, and title, directory, progress, events and exit are still published; `linkAt` and the search are idle while hidden. There is no automatic pause on purpose: code that reads `frames.value` would see a stale frame forever, and a composable that stays composed does not collect less.
- **Configuration**: `TerminalSession.start` takes `cursorShape`, `scrollbackMaxBytes` and `imageStorageLimitBytes` (the defaults are Ghostty's: a block, 10 MB, 320 MB); `Terminal` takes `font` and `fontSize`. `TerminalFont` is public: `bundled()` is loaded once and shared (the fallback cache is synchronized), `system(family)` gives the four real faces of a family (Compose draws them through `SystemFont`, which is experimental), `files(...)` loads files. They **refuse a font that is not monospaced** (the grid cannot be drawn with one); the tests that need one (the characters that a font lacks) use `TerminalFont.systemUnchecked`.

### Search, reading text and many sessions

- **Search** (`session.search`, one per session, made at the first query): `GhosttySearch` is libghostty's (ASCII letters without case, bytes otherwise, no regex), fed **under the lock** and ticked without it. `produceFrame` feeds it in the same lock section as `renderState.update`, so the matches (`TerminalFrame.searchMatches`, one entry per row, outside the rows like the selection) are where they are on that frame, and asks for another frame while the search is not complete (a feed does a bounded amount of work). `TerminalSearchState.selected` is **1-based from the top**, which is `total - index` of libghostty (its index 0 is the newest); `next()` goes down (libghostty's `SELECT_PREV`), `previous()` up, and the first `next()` after a query is the top-most. `SELECT_NEXT` scrolls the viewport itself. `TerminalView` draws the matches (yellow, the selected one orange, over the cells, the text drawn again over them) between the images and the selection. 
- **Reading text**: `readText(first, last)`, `viewportText()`, `screenText()` (rows are in the space of `scrollbar.offset`: 0 is the top of the history) take two `SCREEN` grid refs, make a selection and format it, without moving the viewport; they run under the lock that the reader writes under, and finding a row walks the pages of the history: read a large history in pieces. `lastCommandOutput()` uses a **tracked grid ref** (`GhosttyTrackedRef`, it follows scrolling, reflow and pruning) taken **in the callback of OSC 133;C**, where libghostty says the screen is already up to date: after the write the cursor would have moved on. It needs the shell to mark its commands.
- **Many sessions**: the frame producer runs on `Dispatchers.IO.limitedParallelism(1)` instead of a thread of its own (IO and not Default: `close()` waits for the producer, and many closes at once must not starve the workers that producers need). What is left is **3 platform threads per session**: the reader (pty4j's read is a native `poll(-1)`: a virtual thread would pin a carrier for as long as the program is idle), the writer, and pty4j's process reaper. Going below that means one poller for all the master file descriptors, which bypasses pty4j's read and its closing coordination: not done. Measured with 60 simple sessions: heap per session 0.34 MB visible, 0.09 MB hidden (it was 0.31); threads per session 4.05 before, about 3.2 now. `session.memoryUsage()` has the native memory of a session (resident, compressed, images) for a host that wants to see which ones cost the most, and `TerminalPrimarySelection` can be shared between terminals so that a selection in one is pasted by the middle click of another.

### Saving and restoring a terminal

- `session.snapshot()` gives a `TerminalSnapshot`, `TerminalSession.start(snapshot = …)` starts a **new session** from it. A process cannot be saved: the old program is gone, the new one is `command` (the user's login shell by default) in the snapshot's directory (if it is still there; `directory` overrides), and it starts **below** what the old terminal showed. `toByteArray()` / `fromByteArray()` are the bytes to keep: our envelope (`KATTYSNP`, a version, the fingerprint, the title, the directory, the size, when) and libghostty's own snapshot.
- **libghostty's format has no compatibility promise** ("work in progress"), and the dylib records neither its commit nor a version that changes (`0.1.0-dev`). So the stamp is `GhosttyBuildInfo.fingerprint()`: a **SHA-256 of the dylib that was loaded**. A snapshot of another one is `isRestorable == false` and `start` refuses it with `TerminalSnapshotException`: the host starts a new session. Updating `libghostty-vt/lib` invalidates every saved snapshot. It is not an archive format.
- **What is in it**: both screens, their whole history, the cursor, styles, hyperlinks, the semantic prompt marks (prompt jumps work in the old history), the modes, the colors, the title and directory, the scrollback limits. **What is not**: the Kitty images, the selection, the viewport, and everything the wrapper sets (callbacks, options): `GhosttyTerminal.restore` makes the terminal and then does exactly what the constructor does, with the options of `start` (the host's blink, cursor shape and limits win over what was saved). `lastCommandOutput()` is `null` until the new shell runs a command.
- **The old program's state is taken off the restored terminal** (`RESTORE_RESET`, written to the terminal only, before the new program starts): without it, a snapshot of vim gives the shell mouse reports, application cursor keys, bracketed paste and an alternate screen with no prompt. It leaves the alternate screen (**only if it is on it**: leaving it from the primary screen puts the cursor home), resets the scrolling region (the cursor is saved and put back, since it moves it home), resets the mouse protocols and formats, focus reports, bracketed paste, synchronized output, cursor keys and keypad, insert mode, sets autowrap and shows the cursor, ASCII character sets, pops the Kitty keyboard flags, the cursor style, SGR, and moves to a new row. Origin mode is reset **only if it is set, and the cursor put back**, since resetting it homes the cursor too. Not DECSTR (`CSI ! p`): it homes the cursor and the new program would write over the old content. A mode that a program sets and that is not in the list stays set: add it, with a test.
- The host's size wins: `cols` and `rows` of `start` are the PTY's and the terminal is resized to them, which reflows the old content. `title` and `workingDirectory` start with the snapshot's values (nothing was listening for the callbacks), and the new shell overwrites them.
- **Encoding** (`GhosttyTerminal.snapshot`) must not run while the terminal is written to: `TerminalSession.snapshot()` holds the lock. A snapshot is refused if the VT parser is in the middle of a sequence, so every terminal tracks an unfinished sequence up to 64 KiB (`CONTINUATION_MAX_BYTES`; a 1 MB image transfer neither breaks writing nor is refused for long: only a snapshot taken in the middle of it is, and the session tries again 5 times 20 ms apart). **Decoding** is one-shot with `COMPRESS_HISTORY`, so the restored history is kept compressed (1 MB resident for 10 MB of history). Measured with the default 10 MB history (about 9000 rows of 120 columns): a snapshot is 0.45 MB for plain lines and 3.4 MB for styled wide ones (26 and 61 kB deflated: a host that keeps many should compress), encoding takes 0.4 to 7 ms and restoring 7 to 16 ms.

## The application (`app`, `app-core`)

Read `README.adoc` for what it does, and the design and the brief it follows are the Claude artifacts "ADE — Terminal Manager" and "ADE — implementation brief".
This is how it is built.

- **`app-core` has no Compose** and nothing in it mentions `ghostty-vt`: the model (`Model.kt`: project, workspace, a `PaneNode` tree of splits, `TerminalSpec`), `KattyStore` (one immutable `KattyState` in a `StateFlow`, changed only by its functions), `StateFile` (JSON through a temporary file, a later or damaged file is kept aside, never written over), git (`GitReader` reads the files, it does not start git), the agents (`Agent`, `summarize` of the OSC 7501 records), `Attention`, `Board`, `Palette`, `Usage*`. It is tested without a window.
- **`app` is the windows.** `KattyWindow.kt` is the one place that holds the dialogs, the selection and the shortcuts (before the terminal sees them: they are on the window's `onPreviewKeyEvent`). `terminals/SessionRegistry` keeps **one `TerminalSession` for every terminal of the store**, in whatever workspace, and pauses (`setVisible(false)`) the ones that are not shown; `AgentTracker` follows `programStatus` of each. A pane **never** shows the same session twice (the maximized one is a hollow pane under the scrim): two views would fight over its size.
- **The state of a terminal is what the program says (OSC 7501), nothing else**: no reading of the screen, no hooks installed by the application. A program that does not send it is a shell. `done` and `error` stay until the terminal is in front of the user in a window that has the focus (`markSeen`). What the program says (title, message) is untrusted text: it is shown as text, never as markup.
- **Usage comes from the agents' own commands, which do not cost a turn, and never from a credential.** They run in `KattyDirectories.usageDirectory`, not in a project, since `claude -p` records a session for the directory it runs in. A reading that fails is no reading. Orca's way (the tokens in the keychain, undocumented endpoints) was refused on purpose.
- **A terminal always starts as a plain shell**, and a restored one starts where its shell last was (`setDirectory` follows OSC 7), else in its project's folder, else in the home. The scrollback is not kept.
- **Escape is not used by the window.** Programs in a terminal (agents, vim) use it. A maximized terminal goes back with its button, or a click outside it. F2 renames only when the focus is in the sidebar or the tabs.
- Jewel is `0.41.x`, on the JetBrains Runtime 25 (`app/build.gradle.kts` sets the vendor and passes the toolchain's `javaHome` to Compose's tasks). Its components are used for buttons, menus (`KattyMenu`), the segmented control, checkboxes, text fields and the split layout; the state glyphs, tiles, icons and usage bars are drawn (`app/ui`), with the design's tokens in `KattyColors`.
- Menus are Jewel's `PopupMenu` through `KattyMenu`, submenus included (Jewel's own flyout). Its dismiss callback is made once for the life of the menu: a new object at each drawing makes Jewel's menu controller forget that the pointer is on the menu, so that, with a submenu open, a click on the first menu closes everything instead of choosing the item. In a headless test a click on the first menu while a submenu is open still closes it, with plain Jewel too; a real pointer does too with Jewel 0.41, which is JEWEL-991 ("menus with submenus no longer freeze the parent menu while a submenu is open"), fixed in Jewel 0.42: "Move to workspace" stays broken in the window until `jewel` in `gradle/libs.versions.toml` is bumped to a published 0.42 or later, then retry it by hand.
- **The maximized pane's animation** (`WorkspaceArea`) lays the pane's frame out at its real bounds on every frame (a `layout` modifier that interpolates from `PaneContext.paneBounds` to the area less `MAXIMIZED_MARGIN`), and gives its terminal the final size from the first frame (`PaneView(terminalSize = …)`, clipped by the body), because resizing the terminal with the frame would resize the PTY, and its program, on every frame. A `graphicsLayer` scale was tried and squeezed the text. The pane of the tree stays hollow (and empty) until the way back has finished (`shown` outlives `maximized`). Whether it looks smooth has to be seen in the window.
- A terminal is never given the keyboard by itself: `Terminal(focusOnStart = false)` and the pane decides, or the last one composed takes it.

### Testing the application

- Interaction tests use `runComposeUiTest` with real sessions (`/bin/sh`, `sleep`); rendering tests draw with `render(...)` from `app/src/test/.../ui/Rendering.kt` into `app/build/renders`, in both themes: look at the images when you change how something is drawn.
- A test that builds a `KattyStore` gives it a counter for ids, so that they are the same on every run.
- Compose reads font feature settings **without quotes** (`liga 0`, not `'liga' 0`, which is ignored). A `LazyListState.scrollToItem` during the first layout throws: start the list at its index instead. `ImageComposeScene` does not wait for what a `LaunchedEffect` loads on another thread.
- Running the real app against a throwaway state: `JAVA_TOOL_OPTIONS=-Dkatty.support=/tmp/some-folder ./gradlew :app:run`, with a `state.json` written by hand, and `SHELL=/some/script` to make every terminal a program that prints an OSC 7501 report. Capture the window with `screencapture -l <id>`, never the screen.

## Pitfalls

- **Concurrent Gradle builds in the same directory corrupt each other**: IntelliJ, the MCP server and a hot-reloading app all build in `build/`. Missing class files, `FileNotFoundException` in the Kotlin compiler or a `NoClassDefFoundError` after a successful build mean that happened: `./gradlew :<module>:clean` and run again.
- A Compose composable keeps its focus when the OS window loses its own: use `LocalWindowInfo.current.isWindowFocused` as well to know whether the keys go to it.
- libghostty-vt flags the row that the cursor leaves as dirty, even if it did not change, and its cursor does not blink unless the program asks for it (`TerminalSession.start` turns the default on).
- libghostty-vt's render state only reads the default foreground and background when **both** are set, and keeps what it last read when they are cleared: to go back to the original colors, set them (white on black) instead of clearing them. `TerminalSession.setTheme(null)` does that.
- A character that the terminal's font does not have is given to the system, which picks the **emoji** font for the ones that can be an emoji, so `⏸` (Claude Code's plan mode) was a blue picture. `TextFallback` finds a text font for the ones that are not emoji by default and are not followed by the variation selector 16 (`Character.isEmojiPresentation`). It asks the faces of the font in use (`TerminalFont.faces`), so it must not name a font: the font is a parameter of `Terminal`, and any new way to make a `TerminalFont` has to give the Skia typefaces it loaded. Look for a text font, and do not accept a color one.
- pty4j ignores the size in pixels (its `WinSize` has only cells, and the pixel fields of the pty stay 0), so `TerminalSession.resize` sets the whole window size with its own `ioctl(TIOCSWINSZ)` (`PtyWindowSize.kt`, through FFM, with the **macOS** request number), and falls back to pty4j's when that fails. libghostty answers `CSI 14/16/18 t` and mode 2048 from the size given to `resize`, through a callback that reads copies of it, never the terminal. Programs that do not know the size of a cell (chafa, `kitten icat`…) assume a ratio and draw images squeezed.
- **DEC mode 12 (cursor blinking) is taken out of the program's output** (`OutputTranslator`, in the reader, before `vtWrite`). Emacs sends it on exit as part of the terminfo capability `cnorm` (`ESC [ ? 12 l`, `ESC [ ? 25 h`) and never sets it back, which left the cursor of the shell steady for good. libghostty-vt honors it, while Ghostty's app ignores it when the blink is configured, which `cursorBlink` is: DECSCUSR (`CSI Ps SP q`) is still how a program asks for a steady or a blinking cursor. The translator only touches `ESC [ ? Ps;… h|l` of at most 32 bytes, removes the parameter 12 from the list and passes everything else byte for byte (a query `ESC [ ? 12 $ p` is still answered by the terminal); it holds back a sequence that is cut at the end of a read, which the terminal's own parser would hold as well, and it gives the same result however the stream is cut (a test checks every cut). It does not filter `writeToScreen`.
- **The cursor is given back at the next prompt** (`OutputTranslator` again, because only the stream knows what the cursor was when the mark passed: a callback in `vtWrite` cannot say it when more text follows the mark in the same read). The translator follows DECSCUSR (`CSI Ps SP q`, values over 6 are ignored) and the visibility (`CSI ? 25 h|l`, also in lists) as they pass; at `OSC 133;C` it remembers what the shell had, and at the next `OSC 133;A` it writes, **before the mark**, the sequences that bring it back, if the command changed it. So a program that dies with a bar cursor, or a hidden one, does not leave the prompt with it. It needs the marks of the shell integration; without them nothing changes. A command that sets a style on purpose to keep it is undone at the prompt, by design.
- The generated Java contains macOS system types: generating on another OS gives another file set.
