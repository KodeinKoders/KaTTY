= KaTTY
:toc: macro
:toclevels: 2
:idprefix:
:idseparator: -
:source-highlighter: highlight.js
:icons: font

*A terminal manager for people who run several coding agents at once, written in Kotlin with Compose.*

KaTTY organizes terminals in projects and workspaces, and shows what each agent in them is doing: working, waiting for you, or done.
It displays and arranges terminals, and never reads or writes what an agent says.
The terminals are drawn on a Compose for Desktop `Canvas`, and the window is built with https://github.com/JetBrains/jewel[Jewel].
The terminal emulation is done by https://ghostty.org[libghostty-vt], the library that Ghostty is built on, and the pseudo-terminal is handled by https://github.com/JetBrains/pty4j[pty4j].


== Requirements

* macOS on Apple Silicon.
libghostty-vt is only built for this platform at the moment.
* JDK 25.
It is the LTS that has the final Java FFM API, which the binding to libghostty-vt uses.
Gradle downloads it when it is missing.
The `app` module runs on the JetBrains Runtime 25 (Jewel's window needs it for the title bar), which Gradle downloads too.

NOTE: The application starts `$SHELL -l`, with `TERM=xterm-256color` and `COLORTERM=truecolor`.


== Running

[source,bash]
----
./gradlew :app:run
./gradlew :app:createDistributable   # the application bundle, in app/build/compose/binaries
./gradlew :app:packageDmg            # a disk image
----

The logs are printed on the standard error stream.
Their level is set in `app/src/main/resources/simplelogger.properties`.

`./gradlew build` builds everything and runs the tests, which start programs in a pseudo-terminal, draw frames with Skia in memory and interact with the windows.
The images that the rendering tests draw are kept in `app/build/renders` and `terminal-compose/build/renders`.

The state of the application (the projects, the workspaces, the splits and the settings) is kept in `~/Library/Application Support/KaTTY/state.json`.
The position, size and mode of the window are in `window.json` beside it, and those of the board window in `board-window.json`, so that each opens as it was closed.
`-Dkatty.support=/some/folder` makes it use another folder, to try something without touching it.


== The application

* A *project* is a folder on your disk.
Its *workspaces* hold terminals in a tree of splits that you can drag to resize.
A terminal always starts as a plain shell: you start the agents, and manage git worktrees, yourself.
* The sidebar (or the rail it folds into, or the tabs of the vertical layout) shows how many terminals of each project are in each state.
The *board* shows the agents in a column for their state (a shell has no card), and it can be opened in a window of its own for another screen, where a click on a card selects that terminal in the main window.
The bell lists the agents that need you.
* The state comes from the program in the terminal, which reports it with the escape sequence `OSC 7501`, the _program status_ protocol of libghostty-vt (https://www.superlogical.com/rex/docs/build/program-status[specification]).
A program that does not send it shows as a shell.
* The usage of the agents is read from their own commands, which do not cost a turn: `claude -p /usage`, `agy -p /usage`, and `codex app-server`.
No credential is read.
Gemini CLI and Copilot CLI have no command that says it, so they have no meter.
* Everything is set up from the main menu: the layout, the theme, the default color scheme (811 of them), the font and the ligatures.
* On macOS: ⌘K opens the command palette, ⌘D and ⌘⇧D split, ⌘W closes a terminal, ⌘N makes a workspace, ⌘F finds, ⌘⇧J goes to the next agent that waits.
The palette lists every command with its shortcut.
* At launch the projects, workspaces and splits come back, each terminal with a new shell where the old one was.
The scrollback is not kept.


== Modules

[cols="1,3"]
|===
| Module | Role

| `app`
| The application: Jewel's decorated window, with the sidebar, the workspaces, the board, the palette and the rest of what the design draws.

| `app-core`
| What the application keeps and knows, with no Compose: the projects, workspaces and terminals and their store, the file that keeps them, git, the agents and their states, the usage of each, the palette's matching.

| `terminal-compose`
| `Terminal`, the Compose composable that draws a session with the bundled JetBrains Mono, and sends it the keys that are typed.

| `terminal-themes`
| The color schemes of the https://github.com/mbadolato/iTerm2-Color-Schemes[iTerm2-Color-Schemes] collection (811 of them, in `iterm2-color-schemes`), read from the `.itermcolors` property lists with kotlinx.serialization and xmlutil, as themes for a terminal.

| `terminal`
| `TerminalSession`, which runs a program in a pseudo-terminal, feeds its output to a terminal, and publishes what the screen looks like as immutable frames.
It has its own model of keys and frames, so that nothing above it mentions the binding.

| `ghostty-vt`
| The binding to libghostty-vt, in Java FFM.
The Java part is generated by jextract, and a Kotlin API hides it.
|===

The libghostty-vt library and its headers are in `libghostty-vt`, which is not a Gradle module.
Its `README.adoc` says which Ghostty commit it was built from, and how to update it.


== Status

The terminal runs a shell with colors, text attributes, the 811 iTerm2 color schemes, wide characters, a cursor, resizing with reflow, the keyboard (including the Kitty protocol and dead keys), the mouse, the history and a scrollbar, selecting text, links, images (Kitty graphics, Sixel and iTerm2), search, focus reports, and saving and restoring a terminal.
The application is described above.

What is not done yet:

* input methods other than dead keys (the candidate windows of Chinese, Japanese and Korean input);
* the multipart inline images of iTerm2, and Sixel through tmux's passthrough;
* the `id=` of OSC 8 links, which libghostty does not give;
* shell integration for nushell and elvish;
* other platforms than macOS on Apple Silicon (so the Windows buttons of the title bar cannot be tried);
* hooks that make an agent send `OSC 7501`, for the agents that do not send it on their own: they show as shells until they do;
* the logos of the agents in their original colors (they are drawn in one color each).
